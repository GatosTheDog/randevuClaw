## query-read-timeout-storm — drizzle-orm leaks pg pool client when initial 'begin' statement times out
- **Date:** 2026-07-26
- **Error patterns:** DrizzleQueryError, Query read timeout, begin, rollback, query_timeout, transaction, pool exhaustion, Neon cold start, non-self-resolving storm
- **Root cause:** drizzle-orm's NodePgSession.transaction() (node_modules/drizzle-orm/node-postgres/session.js:180-195) checks out a pool client and runs `await tx.execute(sql\`begin...\`)` BEFORE its own try/finally block; the finally that calls `session.client.release()` never covers that initial begin statement. When begin itself rejects (e.g. client-side query_timeout firing during a Neon compute-suspend cold start), the checked-out client is never released — a permanent leak of one pool slot per occurrence. This compounds within a single burst and across incidents (only a full process restart clears leaked clients), explaining why the "Query read timeout" storm never self-resolved.
- **Fix:** Added `runInTransaction<T>(pool, callback)` helper in src/database/db.ts that checks out the client itself, wraps only that client instance with `drizzle(client, {schema})` (making drizzle's internal `isPool` check false so drizzle skips its own leak-prone release logic), and guarantees `client.release(err)` in its own try/finally regardless of whether begin, the callback, commit, or rollback throws. Swapped all 3 direct `db.transaction()`/`appDb.transaction()` call sites to use it.
- **Files changed:** src/database/db.ts, src/database/queries.ts, src/billing/queries.ts, src/session/slotless-requests.ts, tests/db-transaction-begin-leak.test.ts

## book-session-rollback-timeout — non-reentrant withBusinessContext: nested booking transaction deadlocks on outer FOR UPDATE membership lock
- **Date:** 2026-10-07
- **Error patterns:** DrizzleQueryError, Failed query: rollback, Query read timeout, withBusinessContext, transaction failed/rolled back, elapsedMs 24064, Tool execution threw unexpectedly, book_session, bookSessionInstance, deductSession, membership_ledger, FOR UPDATE, nested transaction, deadlock, Neon pooler, statement_timeout, finite membership, Telegram webhook
- **Root cause:** withBusinessContext is not re-entrant: a call made while another withBusinessContext is ambient opens a SEPARATE transaction on a SEPARATE pooled connection. handleFoundBusiness (src/webhooks/telegram.ts) wraps the whole client AI turn in outer transaction T1; bookSessionTool -> checkEnforcementAndGetMembership -> getActiveMembershipForDeduction takes SELECT ... FOR UPDATE on the client's memberships row in T1, then bookSessionInstance opens nested T2 whose deductSession (INSERT membership_ledger FK key-share, UPDATE memberships) blocks on T1's lock while T1 awaits T2 in JS - an application-level deadlock Postgres cannot detect. On the Neon -pooler endpoint the server-side statement_timeout (10s) and idle_in_transaction_session_timeout (15s) startup params are NOT applied (SHOW statement_timeout = 0; pg_sleep(11) completes), so only the 12s client query_timeout fires; drizzle's ROLLBACK then queues behind the still-blocked statement and times out another 12s (24s total), and the ROLLBACK error masks the original error. Only hits clients with an active finite-pack membership (sessionsRemaining !== null). NOT a recurrence of query-read-timeout-storm (that was a leaked client on a failed BEGIN).
- **Fix:** Added withAmbientBusinessContext in src/database/queries.ts (ALS store now {tx, businessId}): if a withBusinessContext transaction for the SAME business is ambient, run the callback inside it as a SAVEPOINT (failure-isolated), else behave like withBusinessContext. bookSessionInstance (src/session/manager.ts) uses it when the caller passes a non-null activeMembership (read+locked under the caller's ambient tx, so deduction must run in it); null membership keeps the independent short transaction. runInTransaction (src/database/db.ts) now logs the callback's original error when ROLLBACK also fails and replaces it. Regression tests with real Postgres, plus a Neon-pooler emulation (SET statement_timeout=0 / idle_in_transaction_session_timeout=5min on connect) reproduced the exact 24s prod signature pre-fix. Diagnostic tip: when a "Query read timeout" on ROLLBACK appears with elapsedMs ~2x12s, look for nested transactions / row locks held by an outer transaction, not a pool leak.
- **Files changed:** src/database/queries.ts, src/session/manager.ts, src/database/db.ts, tests/session-booking-ambient-lock.test.ts, tests/db-transaction-begin-leak.test.ts

## renewed-sub-cant-book — same-day membership renewal idempotency key collides with itself, rolling back the whole renewal
- **Date:** 2026-08-13
- **Error patterns:** χρειάζεστε ενεργή συνδρομή, membership renewal, createMembership, idempotency_key, membership_ledger, UNIQUE constraint, same-day renewal, WR-05, booking enforcement block despite active package
- **Root cause:** createMembership() (src/billing/queries.ts) derived its membership_ledger idempotencyKey from `${businessId}:${clientPhone}:payment_recorded:${purchaseDate}:${memberId}`. Since memberships.isActive is never set to false anywhere in the codebase, memberId is permanently stable per (businessId, clientPhone) — every renewal for an existing client updates the SAME row, so the key was identical for any two renewal payments on the same Athens calendar day. The ledger insert has no onConflictDoNothing guard, so the second same-day renewal threw on the UNIQUE constraint; since both the ledger insert and the memberships onConflictDoUpdate run inside the same runInTransaction(pool, ...) call, the throw rolled back BOTH — silently discarding the legitimate membership renewal along with the ledger write. Previously flagged but incompletely fixed as WR-05 in the original Phase 7 review (07-REVIEW.md / 07-REVIEW-FIX.md): only a memberId suffix was applied, which fixed the "row replaced" sub-case but left the actual same-row/same-day renewal case broken.
- **Fix:** Made createMembership()'s `idempotencyKey` a required caller-supplied parameter instead of deriving it internally, matching the existing pattern used by deductSession/restoreCredit/linkRescheduledBooking. handleConfirmMembership (payment-flow.ts) now passes `billing:mem_confirm:${callbackQueryId}` — Telegram's callback_query.id is unique per tap and stable across webhook-redelivery retries of that tap, so exact replay is still blocked while two distinct renewals on the same day now each succeed.
- **Files changed:** src/billing/queries.ts, src/telegram/handlers/payment-flow.ts, tests/billing-membership-creation.test.ts, tests/billing-payment-flow.test.ts
