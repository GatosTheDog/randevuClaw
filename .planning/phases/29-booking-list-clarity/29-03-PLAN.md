<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram callback_query.data (any shape) → parseCallbackData() → null | Any Telegram user (client or owner) can send a callback_query with arbitrary, hand-crafted `data`; the null-path recovery message must not leak which businesses/bookings exist, and must correctly route to the admin-vs-client menu based on verified identity, not attacker-supplied data |
| escl:instanceId (owner-only escalation approve tap) → findSessionInstanceById(ownerBusiness.id, instanceId) | instanceId is attacker-controllable input from callback_data; ownerBusiness.id is the webhook-scoped, HMAC-verified business, never re-derived from the untrusted instanceId |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-29-03 | Information Disclosure | handleCallbackQuery's null-path recovery message | low | mitigate | The recovery message text ('Η ενέργεια δεν αναγνωρίστηκε.') is generic and identical regardless of what the malformed callback_data actually contained — no echo of attacker input, no business/booking data disclosed. Admin-vs-client keyboard selection is based on `business.ownerTelegramId === senderTelegramId` (verified identity), never on the callback_data content itself. |
| T-29-04 | Denial of Service | Repeated malformed callback_query taps | low | accept | Each malformed tap produces exactly one recovery message (no escalation, no admin alert, no retry loop) — matches the existing pattern for every other callback branch in this file. Per RESEARCH.md Pitfall 4, this is the accepted, sufficient mitigation; building rate-limiting for this is out of scope for a solo-operator PoC. |
| T-29-06 | Information Disclosure | escl:approve's serviceId lookup (pre-existing, incidentally fixed) | low | mitigate | The old inline join had no businessId filter; findSessionInstanceById(ownerBusiness.id, instanceId) scopes the lookup to the verified owner's own business, so a crafted instanceId belonging to another business now resolves to null instead of leaking that business's serviceId into the exception-booking flow. |

</threat_model>
