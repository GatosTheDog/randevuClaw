| cmenu:cancel:confirm:<bookingId> callback_data → showCancelConfirm | bookingId is attacker-controllable input (callback_data is not restricted to buttons the client was actually shown — any Telegram user can send an arbitrary callback_query.data string); this is the exact boundary Task 2's new ownership guard closes |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-29-05 | Information Disclosure | showCancelConfirm (client-menu.ts) | high | mitigate | Previously had zero ownership check and showed only generic text (low exposure). D-09's enrichment (real date + service name) would turn this into a genuine cross-client data leak if a client crafted a callback_data pointing at another client's bookingId. This plan adds a `booking.clientPhone !== senderTelegramId` guard — identical in shape to handleCancelExecute's own pre-existing guard — BEFORE any booking-derived text is composed, and deliberately returns the same generic response for "not found" and "not yours" to prevent bookingId enumeration via response-shape comparison. |
| T-29-08 | Denial of Service (functional dead-end) | handleClientMenuCallback default case | low | mitigate | An unrecognized clientMenuAction (stale button, future-menu-version mismatch) now resolves to a usable back-to-menu keyboard instead of a bare text line with no forward path — mirrors the identical fix applied to admin-menu.ts's default case in Plan 29-04 (T-29-07). |
