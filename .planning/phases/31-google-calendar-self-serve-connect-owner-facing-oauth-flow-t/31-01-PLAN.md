<objective>
Replace the developer-run `scripts/setup-google-calendar.ts` CLI with a real, owner-facing self-serve flow: a `/calendar` Telegram command plus a Settings menu button (D-01, D-02) that send a signed Google OAuth consent link, and a live `GET /oauth/callback` Express route (D-03) that exchanges the code and stores the refresh token — reusing `exchangeAuthCodeForTokens`/`storeGoogleRefreshToken` from `src/google/oauth.ts` unchanged. Also adds a disconnect action (D-06) with best-effort token revocation (D-07).

No new npm/pip/cargo packages are added (Package Legitimacy Audit: N/A per 31-RESEARCH.md) — this plan only adds Node's built-in `crypto` (already used elsewhere in the codebase) and wires existing, already-implemented Google/Telegram functions into new call sites.

Purpose: Today, connecting a business's Google Calendar requires a developer to run a one-off CLI script with a throwaway local HTTP server (`scripts/setup-google-calendar.ts`). That does not scale past the developer's own machine and blocks any real owner from self-serving. This plan makes calendar connection (and disconnection) a normal, always-available part of the owner's Telegram experience.

Output: A working `/calendar` command, a Settings menu entry, and a production-ready `/oauth/callback` route — an owner never needs a developer's help to connect, disconnect, or reconnect their Google Calendar again.
</objective>

## Artifacts This Phase Produces (Plan 31-01)

- `signOAuthState(businessId: number): string` — new export in `src/google/oauth.ts`. Returns `"${businessId}.${hmacHex}"`, where `hmacHex` is HMAC-SHA256 of the businessId string, keyed by `config.googleClientSecret`. The businessId is embedded in the returned string itself (not just used as HMAC input) because the callback route has no other way to learn which business initiated the flow.
- `verifyOAuthState(state: string): number | null` — new export in `src/google/oauth.ts`. Returns the verified businessId on success, `null` on any failure (malformed format, tampered signature, non-positive-integer businessId). Never throws — explicitly guards `crypto.timingSafeEqual`'s buffer-length precondition before calling it.
- `GET /oauth/callback` — new Express route in `src/server.ts`. Validates `code`/`state` query params, calls `verifyOAuthState`, looks up the business via `findBusinessById`, calls `exchangeAuthCodeForTokens` + `storeGoogleRefreshToken` (both unchanged, reused from `src/google/oauth.ts`), and returns an HTML success/error page (D-04).
- `handleCalendarCommand(chatId: string, business: Business): Promise<void>` — new export in new file `src/telegram/handlers/calendar-connect.ts`. Single state-aware entry point for both the `/calendar` command and the Settings button (D-01): sends a connect link when disconnected, or a disconnect offer when already connected.
- `handleCalendarDisconnect(chatId: string, business: Business): Promise<void>` — new export in `src/telegram/handlers/calendar-connect.ts`. Best-effort Google token revocation (D-07) then unconditional local column clear (D-06).
- `updateBusinessGoogleRefreshToken`'s `refreshToken` parameter in `src/database/queries.ts` widened from `string` to `string | null` to support disconnect.
- `src/telegram/handlers/admin-menu.ts`: `showSettingsMenu` gains a Google Calendar status line + button; `handleMenuCallback` gains `'settings:calendar'` and `'settings:calendar_disconnect'` cases; `reassertMenuButtonAndCommands`'s owner command list gains a `calendar` entry.
- `/calendar` text-command routing block in `handleFoundBusiness` (owner branch) in `src/webhooks/telegram.ts`.
- `tests/google-oauth.test.ts` (extended), `tests/google-oauth-callback.test.ts` (new), `tests/telegram-calendar-command.test.ts` (new).

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Browser (Google OAuth redirect) → GET /oauth/callback | Untrusted query params (`code`, `state`) cross an unauthenticated public HTTP endpoint |
| Telegram owner chat → /calendar command / Settings button | Owner-controlled chat input triggers OAuth URL generation and disconnect actions |
| businesses.googleRefreshToken lifecycle | Long-lived Google credential, written only by /oauth/callback, cleared only by handleCalendarDisconnect |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|--------------|------------------|
| T-31-01 | Spoofing / Tampering | GET /oauth/callback `state` parameter | high | mitigate | `verifyOAuthState` requires an HMAC-SHA256(businessId) signature, checked via `crypto.timingSafeEqual` with an explicit buffer-length guard, BEFORE any code exchange runs. Malformed/tampered/missing state is rejected with a generic 400, never revealing which check failed (31-RESEARCH.md Pitfall 2). |
| T-31-02 | Tampering | OAuth authorization code replay | low | accept | Google's own OAuth2 server invalidates the code after the first successful exchange; no additional application-level mitigation is possible or necessary. |
| T-31-03 | Information Disclosure | logger calls in /oauth/callback and google/oauth.ts | high | mitigate | Never log the raw `code`, `state`, `refreshToken`, or `accessToken` values — only `businessId` and boolean/status fields, mirroring the existing `storeGoogleRefreshToken` logging discipline (oauth.ts line 42). Enforced by Task 1's explicit acceptance criteria and test assertions. |
| T-31-04 | Tampering | GOOGLE_REDIRECT_URI / redirect_uri mismatch | low | accept | Enforced entirely server-side by Google's own OAuth console registration match; no application code can mitigate a misconfigured redirect URI — see this plan's `user_setup` frontmatter for the required manual configuration. |
| T-31-05 | Information Disclosure / Tampering | /oauth/callback success-page HTML interpolating `business.name` | medium | mitigate | `business.name` is HTML-escaped (5-entity substitution, same approach as `src/invites/generator.ts`'s `escapeXml`) before interpolation into the response body — defense-in-depth against a crafted business name producing stored/reflected markup in the success page. |
| T-31-06 | Elevation of Privilege | /calendar command / Settings button reachable by a non-owner | low | accept | Both entry points inherit existing, already-proven gates: the owner branch in `handleFoundBusiness` only reaches command routing after `business.ownerTelegramId === senderTelegramId`, and `handleMenuCallback`'s dispatch is only reached after the same check in the calling callback-query handler (Phase 17/18's established pattern) — no new gate needed. |
</threat_model>
