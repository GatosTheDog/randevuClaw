<objective>
Give clients a lightweight, no-OAuth calendar touchpoint (D-05): when the owner approves a regular (open-slot) booking, the bot sends a hand-rolled RFC 5545 `.ics` file alongside the existing text confirmation, deliverable via a new `sendTelegramDocument` Telegram API wrapper. This is explicitly NOT a second OAuth integration and collects no new GDPR-relevant client data — the `.ics` content is built entirely from data already sent to the client in plaintext chat.

Per this phase's scope note, this feature only needs the single primary booking-confirmation send-site touched (the regular open-slot approve flow in `src/webhooks/telegram.ts`, the same call site that already invokes `syncBookingToCalendar`) — it is logically independent of Plan 31-01's owner OAuth work, sequenced into Wave 2 only because both plans touch `src/webhooks/telegram.ts` (different, non-overlapping regions of the same file).

No new npm/pip/cargo packages are added (Package Legitimacy Audit: N/A per 31-RESEARCH.md) — `.ics` generation is ~30 lines of hand-rolled string building, and Telegram document delivery reuses the exact `fetch`/`FormData` pattern already established by `sendTelegramPhoto`.

Purpose: A client who books through this Telegram-native bot currently has no way to get the appointment onto their own calendar except by manually typing it in. A `.ics` file is a universally-supported, one-tap way to do that, with zero new account linking or data collection.

Output: `src/calendar/ics.ts` (new), `sendTelegramDocument` in `src/telegram/client.ts` (new), and one new call site in the existing booking-approval flow.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Booking data (business.name, service.name — owner-controlled) → .ics VEVENT text fields | Owner-controlled strings interpolated into a document delivered to a third party (the client) |
| Server → Telegram sendDocument API | Outbound file delivery only; no new inbound trust boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|--------------|------------------|
| T-31-07 | Tampering | generateIcsEvent SUMMARY/DESCRIPTION fields | medium | mitigate | `escapeIcsText` escapes RFC 5545 special characters (backslash, semicolon, comma, newline) in `business.name`/`service.name` before interpolation, preventing a crafted business/service name from injecting extra iCalendar properties or corrupting the VEVENT structure. |
| T-31-08 | Information Disclosure | .ics file content | low | accept | Contains only booking date/time/service/business name already known to the client from the existing plaintext chat confirmation — no new PII beyond what's already sent (D-05: explicitly no new GDPR-relevant data collection, no per-client token storage). |
| T-31-09 | Denial of Service | sendTelegramDocument failure blocking the booking confirmation | low | mitigate | `sendBookingConfirmationIcs` wraps generation + send in its own try/catch and never throws (best-effort, non-blocking, mirrors `syncBookingToCalendar`'s established D-15 pattern) — a Telegram API failure here can never prevent or delay the client's text confirmation message, which is sent first. |
</threat_model>
