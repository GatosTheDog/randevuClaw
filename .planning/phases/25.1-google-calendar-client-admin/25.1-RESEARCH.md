# Phase 25.1: Google Calendar for Client & Admin Bookings - Research

**Researched:** 2026-10-02
**Domain:** Google Calendar Integration for Dual-Side Event Sync
**Confidence:** HIGH (existing code verified live; OAuth patterns reused from Phase 3)

## Summary

Phase 25.1 extends the existing Google Calendar sync (Phase 3, code complete but never run live) to deliver calendar events to **both** the owner and client. Owners connect their Google Calendar account from inside the bot (no CLI setup required after Phase 25.1). Confirmed bookings trigger calendar sync for the owner, and clients receive a one-tap "add to my calendar" link. The phase reuses all existing sync infrastructure (sync.ts, poller.ts, oauth.ts) and introduces two new flows: (1) in-bot owner OAuth callback, and (2) client calendar link generation. Session/class bookings are supported with the existing schema. The one-time owner nudge flag requires a new migration.

**Primary recommendation:** Implement as two parallel Task streams — OAuth callback wiring + client link generation — both feeding into the existing sync/poller infrastructure with minimal changes.

## User Constraints (from CONTEXT.md)

### Locked Decisions

**D-01: Client Delivery (Tap-to-Add Link)**
- Client receives a `calendar.google.com/calendar/render?action=TEMPLATE&...` link in the confirmation message
- Link sent only after owner approval, never at request time
- No client email collection, no client OAuth, no `.ics` attachments
- Maintains D-08 from Phase 3: no attendee/email invites

**D-02: Confirmation Timing**
- Client link sent only once booking is confirmed (after owner approval)
- Rejected bookings never produce events or links

**D-03: Reschedule & Cancellation Notifications**
- On reschedule: client receives new link + Greek note asking them to delete the old event
- On cancel: client gets Greek note to remove the event manually
- Client calendars are never modified by the bot (no API calls)

**D-04: Owner OAuth Connect (In-Bot)**
- Owner connects Google Calendar from the owner menu: a button sends OAuth URL
- New callback route on fly.io server exchanges authorization code for refresh token
- Reuses `getOAuth2AuthUrl` / `exchangeAuthCodeForTokens` / `storeGoogleRefreshToken` from Phase 3
- `scripts/setup-google-calendar.ts` remains as a CLI fallback

**D-05: Session Booking Sync**
- Calendar sync extends to class/session bookings (approval/confirm path and cancel/delete paths), not just appointments
- Uses existing `sessionInstances` schema; duration derived from catalog + session time

**D-06: Silent Sync Skip + One-Time Nudge**
- If owner has no Google connection: sync skipped silently, bookings unaffected, client link still works
- Owner gets a single one-time nudge to connect (requires new persisted "nudged" flag)

**D-07: Owner Event Title (Greek-Readable)**
- Title format: service name + client identifier
- Client identifier: client name (if available), fallback to @username, fallback to Telegram ID
- Replaces existing format "Service — Client <phone>"

**D-08: Event Content & Reminders**
- Description includes business name and service name
- 30-minute popup reminder
- No location field (address not in schema, out of scope)

### Pattern 1: OAuth Callback Handler (CSRF + Token Exchange)

**What:** HTTP GET callback from Google OAuth consent flow, validates CSRF state, exchanges auth code for refresh token, stores token, confirms to owner.

**When to use:** Any server-side OAuth flow where the browser is redirected back to your application (Google Calendar, Google Drive, etc.).

**State Format (CSRF protection):**
```typescript
// src/google/callback.ts
import crypto from 'crypto';

export function generateOAuthState(): string {
  // 16 bytes (128 bits) of random data, hex-encoded = 32 hex chars
  // Sufficient entropy for CSRF token; short enough to fit in URL
  return crypto.randomBytes(16).toString('hex');
}

export async function validateOAuthState(state: string, stored: string): boolean {
  // Constant-time comparison to prevent timing attacks
  // Stored state must be retrieved from secure session storage (Redis, in-memory cache, or DB)
  return crypto.timingSafeEqual(Buffer.from(state), Buffer.from(stored));
}
```

**Callback Route (in `src/server.ts`):**
```typescript
app.get('/oauth/google/callback', async (req: Request, res: Response) => {
  const state = req.query.state as string | undefined;
  const code = req.query.code as string | undefined;
  const error = req.query.error as string | undefined;

  // CSRF validation: state must match what was generated before redirecting to Google
  const storedState = await getStoredOAuthState(req.sessionId); // or similar
  if (!state || storedState !== state) {
    return res.status(400).json({ error: 'State mismatch — possible CSRF' });
  }

  // Handle Google's error response
  if (error) {
    logger.warn({ error }, 'Google OAuth returned an error');
    return res.status(400).json({ error: `Authorization failed: ${error}` });
  }

  // Exchange auth code for tokens
  if (!code) {
    return res.status(400).json({ error: 'Missing authorization code' });
  }

  try {
    const { refreshToken } = await exchangeAuthCodeForTokens(code);
    // businessId derived from authenticated owner's Telegram ID (cross-tenant guard)
    const ownerBusiness = await findBusinessByOwnerTelegramId(senderTelegramId);
    if (!ownerBusiness) {
      return res.status(403).json({ error: 'Business not found' });
    }
    await storeGoogleRefreshToken(ownerBusiness.id, refreshToken);
    await sendTelegramMessage(
      senderTelegramId,
      '✅ Google Calendar συνδέθηκε επιτυχώς!'
    );
    return res.status(200).json({ success: true, message: 'Connected' });
  } catch (err) {
    logger.error({ err }, 'OAuth token exchange failed');
    return res.status(500).json({ error: 'Setup failed — see logs' });
  }
});
```

### Pattern 2: Google Calendar TEMPLATE Link Builder

**What:** Constructs a tap-to-add link for the client using `calendar.google.com/calendar/render?action=TEMPLATE`.

**When to use:** Client confirmation messages, reschedule offers, or any user-facing link to add an event to Google Calendar without an API call.

**Example:**
```typescript
// src/calendar/client-link.ts
import { Booking, Service } from '../database/queries';

export interface CalendarLinkOptions {
  bookingId: number;
  serviceName: string;
  calendarDate: string;      // "2026-07-10"
  calendarTime: string;       // "10:00"
  durationMin: number;
  businessName: string;
  clientIdentifier: string;   // client name, @username, or Telegram ID
}

export function buildClientCalendarLink(options: CalendarLinkOptions): string {
  const { serviceName, calendarDate, calendarTime, durationMin, businessName, clientIdentifier } = options;

  // Parse date/time into Google Calendar format (YYYYMMDDTHHMMSS)
  const [year, month, day] = calendarDate.split('-').map(Number);
  const [hours, mins] = calendarTime.split(':').map(Number);
  
  const startDateTime = `${year}${String(month).padStart(2, '0')}${String(day).padStart(2, '0')}T${String(hours).padStart(2, '0')}${String(mins).padStart(2, '0')}00`;
  
  // End time: start + duration (in minutes)
  const endMinutes = hours * 60 + mins + durationMin;
  const endHours = Math.floor(endMinutes / 60);
  const endMins = endMinutes % 60;
  const endDateTime = `${year}${String(month).padStart(2, '0')}${String(day).padStart(2, '0')}T${String(endHours).padStart(2, '0')}${String(endMins).padStart(2, '0')}00`;

  // Event title: service name + client identifier
  const title = `${serviceName} — ${clientIdentifier}`;
  
  // Description: business name and service
  const details = `${businessName}\n${serviceName}`;

  // URL encode parameters (handle Greek text)
  const params = new URLSearchParams();
  params.append('action', 'TEMPLATE');
  params.append('text', title);
  params.append('dates', `${startDateTime}/${endDateTime}`);
  params.append('details', details);
  params.append('ctz', 'Europe/Athens');  // D-08: Greek timezone

  return `https://calendar.google.com/calendar/render?${params.toString()}`;
}
```

### Pattern 3: Session Booking Duration Derivation

**What:** For session (class) bookings, compute event duration from the session catalog (fixed start time) and a known end time or default duration.

**When to use:** Session/class bookings where the duration is fixed per catalog entry, not per booking.

**Implementation:**
```typescript
// src/calendar/session-duration.ts
import { db } from '../database/db';
import { sessionCatalog } from '../database/schema';
import { eq } from 'drizzle-orm';
import { addMinutesToLocalTime } from './sync';  // reuse existing helper

export async function getSessionDurationMin(sessionInstanceId: number): Promise<number | null> {
  // sessionInstances.catalogId → sessionCatalog.startTime + capacity
  // For PoC: assume session duration = service.durationMin (same as appointment duration)
  // Future: add explicit sessionCatalog.durationMin column if sessions have variable lengths
  
  const catalog = await db
    .select()
    .from(sessionCatalog)
    .where(eq(sessionCatalog.id, catalogId))
    .limit(1);

  return catalog[0]?.service?.durationMin ?? null;  // Fallback to service duration
}
```

### Anti-Patterns to Avoid

- **Do NOT cache refresh tokens in memory or process state.** Refresh tokens are long-lived credentials — store only in the database with no copies in application memory. If a refresh token leaks or is revoked by the user, the DB should reflect the current state immediately.

- **Do NOT make calendar sync a blocking operation.** D-15 from PROJECT.md mandates best-effort, never-throws behavior. A Google Calendar API timeout or auth failure must not block booking confirmation, client notification, or webhook response to Telegram.

- **Do NOT URL-encode Greek text manually.** Use `URLSearchParams` or `encodeURIComponent()` — both handle UTF-8 Greek characters correctly. Manual string manipulation (e.g., `.replace(/\s/g, '+')`) will mangle non-ASCII text.

- **Do NOT store or log refresh tokens.** Treat like passwords — never include in exception messages, HTTP logs, or structured logs. Use the logger.info/error pattern of naming fields (e.g., `{ businessId, action: 'storeRefreshToken' }` without the token value itself).

- **Do NOT assume session bookings have a `durationMin` field on sessionInstances.** Derive it from the associated service or catalog; sessionInstances only stores `sessionDate` and `sessionTime`. Schema does not include session-specific duration overrides.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| OAuth 2.0 token exchange | Custom HTTP parsing, manual state validation | `exchangeAuthCodeForTokens()` from `src/google/oauth.ts` (Phase 3) | Already tested; includes error handling for "no refresh token" case (e.g., subsequent authorizations without `prompt=consent`) |
| URL-encoded query strings with Greek text | Manual string concatenation + `.replace()` | `URLSearchParams` (native Node.js) | Handles UTF-8 encoding automatically; safer for non-ASCII text |
| Google Calendar event creation/update/delete | Custom REST calls via http/https module | `google.calendar()` from `googleapis` library | Handles auth, pagination, retries; abstracts API version changes |
| Timezone-aware date/time math (DST) | Manual hour/minute/day rollover | `addMinutesToLocalTime()` from `src/calendar/sync.ts` (existing) | Already DST-safe via `addCalendarDays` utility; tested for midnight crossings |
| Storing/retrieving OAuth state for CSRF | In-memory Set or process variable | Combination of crypto.randomBytes + per-owner session storage or short-lived DB entry | Process-level state is lost on server restart; CSRF token must be validated exactly once before token exchange |

**Key insight:** Google Calendar integration looks deceptively simple ("just make HTTP calls to insert events") but has several non-obvious failure modes — timezone DST bugs, session duration ambiguity, refresh token expiry cycles, URL encoding edge cases, and OAuth state management race conditions. Reuse existing patterns from Phase 3; they've already navigated these pitfalls.

## Common Pitfalls

### Pitfall 1: Session Duration Ambiguity
**What goes wrong:** Session bookings (class bookings) don't have an explicit `durationMin` on the `sessionInstances` table. Attempting to use `booking.sessionInstanceId` without resolving the associated service duration leads to a NULL or 0-minute event in Google Calendar.

**Why it happens:** Sessions inherit duration from their catalog's service, but the schema denormalizes only `sessionDate` and `sessionTime` onto the instance row to avoid a JOIN on every availability query.

**How to avoid:** Before calling `syncBookingToCalendar` for a session booking, fetch the service duration via `sessionInstances → sessionCatalog → services → durationMin`. A helper function `getSessionDurationForBooking(booking)` should abstract this lookup.

**Warning signs:** Tests that create session bookings without a service, or that mock a session instance without a valid FK chain.

### Pitfall 2: Phase 26 Reschedule Approval Interaction
**What goes wrong:** Phase 26 (next phase) reverses the Phase 22 auto-approval decision for reschedules — reschedules now require owner approval like new bookings. If Phase 25.1 sends the new calendar link in the client confirmation *before* the owner approves the reschedule, the link is sent even if the reschedule is later rejected.

**Why it happens:** The reschedule approval flow in Phase 26 is not yet implemented; it's easy to assume reschedules still auto-confirm.

**How to avoid:** Timing check: client calendar link MUST be sent only after `booking.bookingStatus` is 'confirmed', not 'pending_owner_approval'. Reschedule flow must wait for owner approval before any client link is sent.

**Warning signs:** Seeing client links in pending bookings (via log inspection) or client messages referencing reschedules that never completed.

### Pitfall 3: Refresh Token Expiry After 7 Days (Testing vs. Production)
**What goes wrong:** Google's OAuth consent screen has two publishing statuses:
- **Testing:** Refresh tokens expire after 7 days of inactivity.
- **Production (verified):** Refresh tokens are long-lived (months/years).

For the PoC (Testing status), a refresh token obtained on day 1 stops working on day 8 if unused. This breaks the demo if the live test is delayed past a week.

**Why it happens:** Google's security policy — Testing apps are assumed to be development/throwaway; they don't warrant eternal token storage.

**How to avoid:** Document the Testing-status caveat in VERIFICATION.md (human-readable note, not code). If demo delay > 7 days, the owner must re-authorize via the in-bot connect flow (trivial, 30 seconds). For production (v1.7 post-PoC), move the Google Cloud project to Production status.

**Warning signs:** "Calendar sync worked yesterday but stopped today" messages with no code changes.

### Pitfall 4: Client Name Availability at Sync Time
**What goes wrong:** Sync can be triggered from the poller (async, hours later) or directly after approval (sync). In the poller context, `booking.clientPhone` is the Telegram ID as a string, but the `clientBusinessRelationships.clientName` is nullable and updated only on new messages from the client. A client who booked via AI but never sent a message after the booking has no name in the relationship row.

**Why it happens:** Client names are updated on each incoming message via message handler, but if the client hasn't interacted after booking confirmation, there's no recent name update.

**How to avoid:** At sync time, resolve client name via a helper that queries `clientBusinessRelationships` and falls back to the Telegram ID. The resolver should handle NULL `clientName` gracefully.

**Warning signs:** Tests that mock bookings without corresponding `clientBusinessRelationships` rows, or that expect a name to be present when it's nullable.

### Pitfall 5: URL Length Limits in Telegram Callback Buttons
**What goes wrong:** Calendar links with Greek text and long event titles can exceed Telegram's 64-byte limit for inline button callback_data. (Note: the client link goes in the message text, not a button, so it's not subject to the 64-byte constraint, but if a future UI adds a "copy to calendar" button, this becomes relevant.)

**Why it happens:** Greek characters in UTF-8 take 2 bytes per character (vs. 1 for ASCII). A 30-character Greek title + URL parameters can quickly exceed limits.

**How to avoid:** Keep event titles concise (service name + 1-2 char abbreviation for client identifier instead of full name, if needed). For Phase 25.1, the link goes in message body (unlimited), so this is not a blocker.

**Warning signs:** Telegram error "callback_data exceeds maximum length" when testing with long service names or multi-character client names.

### Pitfall 6: Timezone DST Edge Case (March/October in Greece)
**What goes wrong:** Using naive date arithmetic without DST awareness can produce off-by-one-hour events in Google Calendar during DST transitions. Greece observes DST: last Sunday of March (advance 1h), last Sunday of October (revert 1h).

**Why it happens:** Event times are stored as local time ("HH:MM", e.g., "10:00") + local date ("YYYY-MM-DD"). The `addMinutesToLocalTime` helper correctly handles midnight crossings, but does NOT adjust for DST.

**How to avoid:** Google Calendar API accepts `timeZone: 'Europe/Athens'` in the request, which tells Google to interpret the dateTime as wall-clock time in Athens and handle DST internally. The code already does this; ensure no changes accidentally remove the timeZone field.

**Warning signs:** Events that are off by 1 hour during DST transition weeks (check logs with dates near March 25 or October 27).

### Example 1: OAuth State & Callback Flow

**Source:** `scripts/setup-google-calendar.ts` + new Phase 25.1 callback handler

```typescript
// src/google/callback.ts
import crypto from 'crypto';
import { Request, Response } from 'express';
import { config } from '../config';
import { findBusinessByOwnerTelegramId } from '../onboarding/queries';
import { exchangeAuthCodeForTokens, storeGoogleRefreshToken } from './oauth';
import { sendTelegramMessage } from '../telegram/client';
import { logger } from '../utils/logger';

// Temporary in-memory store for state (CSRF tokens).
// For production, use Redis or DB with 10-minute expiry.
const oauthStateStore = new Map<string, { businessId: number; createdAt: Date }>();

export function generateOAuthStateForOwner(ownerTelegramId: string): string {
  const state = crypto.randomBytes(16).toString('hex');
  // In production, map state to (ownerTelegramId, businessId) in Redis with 10min TTL
  // For PoC, keep in-process only
  oauthStateStore.set(state, { businessId: 0, createdAt: new Date() });
  return state;
}

export async function handleGoogleOAuthCallback(req: Request, res: Response): Promise<void> {
  const state = req.query.state as string | undefined;
  const code = req.query.code as string | undefined;
  const error = req.query.error as string | undefined;

  if (!state || !oauthStateStore.has(state)) {
    logger.warn({ state }, 'OAuth callback: invalid or missing state (CSRF check failed)');
    res.status(400).send('Invalid state — possible CSRF attack. Please try again.');
    return;
  }

  oauthStateStore.delete(state); // One-time use only

  if (error) {
    logger.warn({ error }, 'Google OAuth consent denied by user');
    res.status(400).send(`Authorization declined: ${error}. Please try again.`);
    return;
  }

  if (!code) {
    res.status(400).send('Missing authorization code.');
    return;
  }

  try {
    // Exchange code for tokens (from Phase 3's oauth.ts)
    const { refreshToken } = await exchangeAuthCodeForTokens(code);

    // Determine which owner this is (in production, store ownerId in the state somehow)
    // For PoC: extract from an additional query param or a session cookie
    // For now, this is a design decision left to Claude's Discretion.
    // Placeholder: assume the owner is authenticated via a separate session mechanism
    const ownerTelegramId = req.query.owner_id as string | undefined;
    if (!ownerTelegramId) {
      res.status(400).send('Missing owner identification.');
      return;
    }

    const ownerBusiness = await findBusinessByOwnerTelegramId(ownerTelegramId);
    if (!ownerBusiness) {
      res.status(403).send('Business not found.');
      return;
    }

    // Store refresh token (from Phase 3's oauth.ts)
    await storeGoogleRefreshToken(ownerBusiness.id, refreshToken);

    // Notify owner via Telegram
    await sendTelegramMessage(
      ownerTelegramId,
      '✅ Google Calendar συνδέθηκε με επιτυχία! Οι κρατήσεις σας θα εμφανίζονται στο ημερολόγιό σας.'
    );

    res.status(200).send(`
      <html>
        <head><title>Google Calendar Connected</title></head>
        <body>
          <h1>✅ Συνδέθηκε!</h1>
          <p>Το Google Calendar συνδέθηκε με επιτυχία. Μπορείτε να κλείσετε αυτό το παράθυρο.</p>
        </body>
      </html>
    `);
  } catch (err) {
    logger.error({ err, state }, 'OAuth callback: token exchange failed');
    res.status(500).send('Setup failed — see server logs.');
  }
}
```

```typescript
export async function buildClientCalendarLinkForBooking(
  booking: Booking,
  service: Service,
  business: Business

  // Resolve client identifier (name → @username fallback → Telegram ID)
  const clientIdentifier = await getClientName(business.id, booking.clientPhone) 
    ?? booking.clientPhone;

    serviceName: service.name,

    calendarTime: booking.calendarTime,
    durationMin: service.durationMin,
    businessName: business.name,
    clientIdentifier,
  });

export interface CalendarLinkOptions {
  serviceName: string;
  calendarDate: string;    // "2026-07-10"
  calendarTime: string;    // "10:00"
  durationMin: number;
  businessName: string;
  clientIdentifier: string;
}

export function buildClientCalendarLink(options: CalendarLinkOptions): string {
  const { serviceName, calendarDate, calendarTime, durationMin, businessName, clientIdentifier } = options;

  // Parse date/time: "2026-07-10" + "10:00" → YYYYMMDDTHHMMSS
  const [year, month, day] = calendarDate.split('-').map(Number);
  const [hours, mins] = calendarTime.split(':').map(Number);
  const startDateTime = `${year}${String(month).padStart(2, '0')}${String(day).padStart(2, '0')}T${String(hours).padStart(2, '0')}${String(mins).padStart(2, '0')}00`;

  // Compute end time
  const totalMins = hours * 60 + mins + durationMin;
  const endHours = Math.floor(totalMins / 1440) > 0 ? Math.floor(totalMins / 60) : Math.floor(totalMins / 60);
  const endMins = totalMins % 60;
  const endDateTime = `${year}${String(month).padStart(2, '0')}${String(day).padStart(2, '0')}T${String(endHours).padStart(2, '0')}${String(endMins).padStart(2, '0')}00`;

  const title = `${serviceName} — ${clientIdentifier}`;
  const details = `${businessName}\n${serviceName}`;

  const params = new URLSearchParams();
  params.append('action', 'TEMPLATE');
  params.append('text', title);
  params.append('dates', `${startDateTime}/${endDateTime}`);
  params.append('details', details);
  params.append('ctz', 'Europe/Athens');

  return `https://calendar.google.com/calendar/render?${params.toString()}`;
}
```

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes | OAuth 2.0 with `prompt=consent` + `access_type=offline` (existing in oauth.ts) |
| V3 Session Management | yes | Refresh token stored in DB, no in-memory caching; state CSRF tokens one-time use |
| V4 Access Control | yes | businessId ownership derived from authenticator (ownerTelegramId), not untrusted callback_data |
| V5 Input Validation | yes | Calendar link parameters URL-encoded via `URLSearchParams` (native); no manual string concatenation |
| V6 Cryptography | yes | HMAC webhook verification (existing T-04-10), state token via `crypto.randomBytes` |
| V9 Data Protection | yes | Refresh tokens never logged; treated like passwords; only read by sync.ts |

### Known Threat Patterns for Google Calendar Integration

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| OAuth refresh token leak (code, logs, memory) | Disclosure | Never log, never cache in-process, store only in DB with no copies elsewhere (sync.ts reads fresh on each call) |
| CSRF attack on OAuth callback | Tampering | Random state token (16 bytes), validated before token exchange, one-time use (revoked after exchange) |
| Cross-tenant data leak (owner A's token used for owner B's business) | Disclosure, Elevation | businessId derived from authenticated ownerTelegramId, never from untrusted callback_data (mirrors Phase 7 pattern T-07-06) |
| Malformed calendar link with injection (e.g., `&description=<script>alert()</script>`) | Tampering, Execution | URLSearchParams automatically encodes special characters; no manual concatenation |
| Refresh token expiry unhandled (7-day Testing limit) | Denial of Service | Document in VERIFICATION.md as human-controlled; PoC mitigated by re-auth flow (60s, trivial) |
| Client calendar link spoofed (fake link sent to client) | Tampering, Fraud | Link is sent from the trusted Telegram bot account; client receives via authenticated bot webhook (hard to spoof). No additional validation needed. |

### Threat Model Notes

- **Data in transit:** Google Calendar API calls use HTTPS (enforced by googleapis library); webhook to Telegram uses HTTPS (enforced by Telegram). No plaintext channels.
- **Data at rest:** Refresh token stored in Neon DB (TLS encryption in transit, encryption at rest via Neon's provider); no sensitive data logged.
- **Privilege escalation:** Owner OAuth consent is explicit (user clicks "Allow"); token is scoped to calendar.events.* only (minimal scope, no Gmail/Drive access).

## Open Questions

1. **OAuth State Storage for Multi-Server Deployment**
   - What we know: PoC assumes single-server fly.io deployment; state can be in-memory
   - What's unclear: If the platform scales to multiple fly.io Machines or undergoes a restart mid-OAuth, state is lost. Should Phase 25.1 implement Redis/DB state storage now, or defer to v1.8?
   - Recommendation: For PoC, use in-memory Map with 10-minute expiry (acceptable risk given single-server deployment). Add a TODO to migrate to Redis if multi-server deployment is planned.

2. **Session Duration Derivation**
   - What we know: Session instances inherit duration from their service
   - What's unclear: Are there cases where a session has a different duration than the catalog's service? (e.g., a shortened session, or a multi-part class spanning two time slots?)
   - Recommendation: For Phase 25.1, assume 1:1 mapping (session duration = service duration). If Phase 26+ introduces variable-duration sessions, add `sessionCatalog.durationMinOverride` column.

3. **Client Name in Async Poller Context**
   - What we know: Client names are updated on each incoming message from the client
   - What's unclear: If the poller syncs a booking 12 hours after confirmation, but the client hasn't sent any messages since, should the calendar event use the name from the booking time or the current name?
   - Recommendation: Always fetch current name at sync time (mirrors the existing pattern of fetch-fresh data); this ensures the calendar event reflects the latest-known client identifier.

4. **Reschedule & Calendar Links (Phase 26 Interaction)**
   - What we know: Phase 26 will make reschedules require owner approval
   - What's unclear: When should the client receive the new calendar link? Option A: after client submits reschedule (link is "tentative" until owner approves). Option B: only after owner approves (client link is "final"). Which aligns with D-02 timing?
   - Recommendation: Option B is safer — send client link only after approval, consistent with D-02. Implementer of Phase 26 should coordinate with this decision.
