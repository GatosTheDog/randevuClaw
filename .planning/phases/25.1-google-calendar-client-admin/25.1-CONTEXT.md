# Phase 25.1: Google Calendar for Client & Admin Bookings - Context

**Gathered:** 2026-10-02
**Status:** Ready for planning

<domain>
## Phase Boundary

Confirmed bookings (appointments AND class/session bookings) appear in the owner's Google Calendar automatically, and clients get a one-tap "add to my Google Calendar" link with their confirmation. Owner connects Google Calendar from inside the bot (no CLI). Owner sync code already exists but has never run live.

</domain>

<decisions>
## Implementation Decisions

### Client delivery
- **D-01:** Client gets a tap-to-add Google Calendar template link (`calendar.google.com/calendar/render?action=TEMPLATE&...`) in the confirmation message. No client email collection, no client OAuth, no `.ics`. D-08 (no attendee/email invite) from Phase 3 stays in force.
- **D-02:** Link is sent only once the booking is confirmed (after owner approval), never at request time, so rejected bookings never produce events.
- **D-03:** On reschedule, client receives the new link plus a Greek note asking them to delete the old event. On cancel, client gets a Greek note to remove the event. Client calendars are never modified by the bot.

### Admin connect & scope
- **D-04:** Owner connects Google Calendar from the owner menu: a button sends an OAuth link; a new callback route on the fly.io server exchanges the code and stores the refresh token (reusing `getOAuth2AuthUrl` / `exchangeAuthCodeForTokens` / `storeGoogleRefreshToken`). `scripts/setup-google-calendar.ts` stays as a fallback.
- **D-05:** Calendar sync extends to class/session bookings (approval/confirm path and cancel/delete paths), not just appointments.
- **D-06:** If the owner has no Google connection, sync is skipped silently, bookings are unaffected, the client link still works, and the owner gets a single one-time nudge to connect (needs a persisted "nudged" flag).

### Event content
- **D-07:** Owner event title becomes Greek and readable: service name plus client name/@username, falling back to the Telegram id when no name is available (replaces `Service — Client <phone>`).
- **D-08:** Description includes business name and service. Add a 30-minute popup reminder. No location field (no address in schema; out of scope).

### Claude's Discretion
- OAuth `state` format/CSRF protection for the new callback, callback route path, and success page/message wording.
- Link-builder placement (new util vs inside `src/calendar/`), timezone handling (Europe/Athens), and event duration for session bookings.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `getOAuth2AuthUrl` / `exchangeAuthCodeForTokens` / `storeGoogleRefreshToken`: full OAuth flow, currently only used by the CLI script
- `syncBookingToCalendar` / `deleteBookingFromCalendar`: idempotent update-or-insert keyed on `googleCalendarEventId`
- `calendarSyncStatus` + retry poller: existing failure-recovery for sync

### Established Patterns
- Calendar failures are non-blocking; booking DB state is source of truth
- OAuth client always built fresh per business (T-03-05)
- Greek-only user-facing text

### Integration Points
- Owner menu (admin menu handlers) for the connect button
- Confirmation message sends in the approval path for the client link
- New HTTP route in `src/server.ts` for the OAuth callback; Google console redirect URI must match `config.googleRedirectUri`

</code_context>
