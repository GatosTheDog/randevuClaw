# Phase 25.1: Code Review Report

**Reviewed:** 2026-10-02
**Depth:** standard
**Files Reviewed:** 23
**Status:** issues_found

## Summary

Phase 25.1 implements Google Calendar OAuth integration with in-bot connect flow, calendar sync, and owner nudges. The implementation demonstrates strong security practices for OAuth state management (single-use, database-backed, SHA-256 hashed), webhook transaction safety, and sensitive data protection. However, one critical race condition and three quality issues were identified. The OAuth callback security model is sound, state consumption is atomic, and error handling in calendar sync is defensive. All sensitive data (tokens, states, error details) is properly protected from logs.

## Critical Issues

### CR-01: Race Condition in Google Calendar Nudge — Stale Business Object

**File:** `src/calendar/confirmation.ts:69-75` and `src/calendar/owner-nudge.ts:37-48`

**Issue:** The `processBookingConfirmedForCalendar` function receives a `business` parameter that may be stale. When calling `maybeSendGoogleCalendarNudge(business)` at line 71, the business object is checked for `googleRefreshToken` inside owner-nudge.ts line 39. However, if another process completes Google OAuth between the initial business fetch and the nudge check, the stale object will have a null token, causing the nudge to send even though the calendar is already connected.

Scenario:
1. Booking confirmation fetches business (token is null)
2. Owner completes OAuth in parallel → token is set in DB
3. Confirmation code still has stale business object with null token
4. Nudge function checks stale object and sends (incorrectly)

While the nudge uses an atomic claim (so it only sends once), this race condition causes the owner to receive a misleading "connect your calendar" message when already connected.

**Fix:**
Inside `maybeSendGoogleCalendarNudge`, re-fetch the business from the database before checking the token:

```typescript
export async function maybeSendGoogleCalendarNudge(business: Business): Promise<boolean> {
  try {
    // Re-fetch to avoid stale token check
    const current = await findBusinessById(business.id);
    if (!current || current.googleRefreshToken) return false;
    if (!current.ownerTelegramId || !current.botToken) return false;

    const claimed = await claimGoogleCalendarNudge(current.id);
    if (!claimed) return false;

    try {
      await sendConnectMessage(current.ownerTelegramId, current.botToken, GCAL_NUDGE_GREEK);
      return true;
    } catch (err) {
      // ... rest of error handling
    }
  } catch (err) {
    logger.error(...);
    return false;
  }
}
```

### WR-01: Code Duplication of Callback Data Size Validation

**File:** `src/telegram/handlers/admin-menu.ts:37-44` and `src/telegram/handlers/client-menu.ts:53-59`

**Issue:** The `assertCallbackDataSize` function is duplicated verbatim in both files. The client-menu.ts includes a comment (line 51-52) explaining it was copied because it's not exported from admin-menu.ts, but this creates maintenance burden and inconsistency risk.

**Fix:**
Extract to a shared utility:

```typescript
// src/telegram/handlers/callback-utils.ts
export function assertCallbackDataSize(data: string): void {
  if (Buffer.byteLength(data, 'utf8') > 64) {
    logger.warn(
      { data, bytes: Buffer.byteLength(data, 'utf8') },
      'callback_data exceeds 64 bytes — Telegram will reject'
    );
  }
}
```

Then import in both files instead of duplicating.

### WR-02: Missing Positive Duration Validation in Schema

**File:** `src/database/schema.ts:129`

**Issue:** The `services.durationMin` column is defined as a plain integer with no CHECK constraint:

```typescript
durationMin: integer('duration_min').notNull(),
```

A service can be created with zero or negative duration, which could produce unexpected behavior:
- Negative durations in `addMinutesToLocalTime` will roll to the previous day (mathematically correct but semantically wrong)
- Zero-duration services create calendar events with start time = end time
- Data quality issue that should be prevented at the schema level

**Fix:**
Add a CHECK constraint in the schema or in a migration:

```sql
ALTER TABLE services ADD CONSTRAINT services_duration_positive CHECK (duration_min > 0);
```

Or in Drizzle schema, add validation at the business logic layer (Zod schema for service creation).

### WR-03: describeGoogleError May Leak Sensitive Information via .message Field

**File:** `src/google/errors.ts:32`

**Issue:** The function extracts and logs `err.message` from arbitrary error objects:

```typescript
message: truncate(err instanceof Error ? err.message : typeof record.message === 'string' ? record.message : '[non-error object]'),
```

If a non-Error object with a `.message` field is passed (e.g., a gaxios error object with partial data), the message could contain sensitive information like auth headers, partial tokens, or request details.

While gaxios errors are usually Error instances and the current code path typically only accesses `response`, this is a fragile assumption.

**Fix:**
Whitelist known safe message sources and explicitly exclude sensitive fields:

```typescript
export function describeGoogleError(err: unknown): GoogleErrorDescription {
  // ... existing code ...
  
  let message = '[unknown error]';
  if (err instanceof Error) {
    message = truncate(err.message);
  } else if (isRecord(err)) {
    const msg = err.message;
    // Only include message if it's clearly safe (short, no special chars)
    if (typeof msg === 'string' && msg.length < 200 && !/[Aa]uth|token|secret/i.test(msg)) {
      message = truncate(msg);
    }
  }
  
  const description: GoogleErrorDescription = { message };
  // ... rest of function ...
}
```

### WR-04: OAuth State Expiry Boundary Condition

**File:** `src/database/queries.ts:773`

**Issue:** The state consumption query uses `gt(googleOauthStates.expiresAt, new Date())`:

```typescript
and(eq(googleOauthStates.stateHash, stateHash), gt(googleOauthStates.expiresAt, new Date()))
```

This is `expiresAt > now`, which means a state expires at exactly the `expiresAt` timestamp (inclusive). If the database server clock and application server clock differ by a few milliseconds, a state could be rejected as "expired" when it should still be valid, or vice versa.

The window is small (milliseconds) but in high-concurrency scenarios near expiry, this could cause false rejections.

**Fix:**
Add a small grace window (e.g., 1 second):

```typescript
const now = new Date();
const graceWindow = new Date(now.getTime() - 1000); // Allow 1 sec clock skew

const rows = await db
  .delete(googleOauthStates)
  .where(
    and(
      eq(googleOauthStates.stateHash, stateHash),
      gt(googleOauthStates.expiresAt, graceWindow)
    )
  )
  .returning({ businessId: googleOauthStates.businessId });
```

## Info

### IN-01: OAuth Callback Does Not Validate Google Error Parameter Format

**File:** `src/google/callback.ts:100`

**Issue:** When Google denies consent, the error parameter is logged with truncation but no format validation:

```typescript
logger.warn({ businessId, googleError: error.slice(0, 64) }, 'Google OAuth consent denied');
```

While the slice limits output to 64 characters and it's only logged (not reflected to user), it's still logging user-controlled input. Should validate the error is one of the known Google OAuth error codes.

**Suggestion:**
Whitelist known error codes:

```typescript
const knownErrors = ['access_denied', 'invalid_scope', 'server_error', 'temporarily_unavailable'];
const errorCode = knownErrors.includes(error) ? error : 'unknown';
logger.warn({ businessId, googleError: errorCode }, 'Google OAuth consent denied');
```

### IN-02: Magic Numbers in Timeout Constants Lack Rationale Comments

**File:** `src/google/constants.ts:6,9`

**Issue:** The timeout constants are defined with brief comments:

```typescript
export const GOOGLE_API_TIMEOUT_MS = 8000;  // Bound for every Calendar and token call
export const GOOGLE_OAUTH_STATE_TTL_MS = 10 * 60 * 1000;  // Lifetime of pending OAuth state
```

While the code comment at line 3-5 mentions the 15-second webhook idle_in_transaction timeout, the relationship is not explicitly documented in the constant definitions. Makes it harder for future maintainers to understand why 8s was chosen.

**Suggestion:**
Add inline comments explaining the rationale:

```typescript
// 8s timeout ensures we complete within the 15s idle_in_transaction_session_timeout
// (T-25.1-07). The 5-minute poller provides retry logic for transient failures.
export const GOOGLE_API_TIMEOUT_MS = 8000;

// 10-minute window allows owner time to open browser and complete OAuth consent.
// Shorter than Google's typical session timeouts to prevent accidental replay.
export const GOOGLE_OAUTH_STATE_TTL_MS = 10 * 60 * 1000;
```

## Positives (No Fix Required)

The implementation demonstrates strong security practices in several areas:

1. **OAuth State Security** (oauth-state.ts, queries.ts): Single-use state with SHA-256 hash storage, atomic DELETE...RETURNING consumption, no raw state logging. Correct implementation of OWASP OAuth recommendations.

2. **Sensitive Data Protection**: All token, state, and error objects are properly sanitized before logging. The `describeGoogleError` pattern prevents leaking gaxios request bodies. Tokens never appear in logs or URL paths.

3. **Webhook Transaction Safety** (queries.ts:649-657, 643-648): Calendar sync status writes use `getConn()` to join the transaction instead of a separate admin pool, preventing deadlock when a booking row is locked during confirmation.

4. **Calendar Sync Error Handling** (sync.ts, poller.ts): Per-booking and per-business try/catch isolation ensures one failure doesn't block others. Revocation detection immediately clears tokens and notifies the owner. Retry budget (max 10 attempts, 50-minute window per poller) prevents Google Calendar quota exhaustion.

5. **RLS on OAuth State Table** (migration 0013, schema.ts): No policies and no GRANT to app role ensures the application cannot read or forge OAuth states. Correct use of database-enforced access control.

6. **Idempotency** (scripts/apply-sql-migration.ts, verify-schema-25-1.ts): Migration script properly guards ALTER TABLE operations with DO blocks. Verification script confirms all three components (nudge column, states table, RLS) are in place.
