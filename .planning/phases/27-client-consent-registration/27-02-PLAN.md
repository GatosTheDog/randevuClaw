<objective>
Wire the hard Ναι/Όχι consent gate (COMP-01, D-01/D-02/D-03) into both client entry points — `/start` and free-form chat — so a client only ever reaches the menu or an AI reply after explicitly accepting, and completing the loop so acceptance (D-01) sets the SAME `consentGiven` flag that also serves as the opt-in/registration flag (COMP-02).

Purpose: Plan 27-01 made the schema/query layer capable of tracking real opt-in state; this plan is what actually makes that state observable and enforced from the client's point of view, closing the ROADMAP Phase 27 gap end-to-end.
Output: A working consent gate on `/start`, an equivalent hard gate on free-chat (replacing the old soft/prepended notice), and the `consent:yes`/`consent:no` callback handling that completes the opt-in.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Unauthenticated Telegram callback_query → consent:yes/consent:no handler | The `consent:yes`/`consent:no` callback_data carries no ids at all — the handler trusts only the webhook-scoped, HMAC-verified `business` param (from Step 3 of `handleTelegramWebhookPost`) plus Telegram's own `callback_query.from.id` for `senderTelegramId` |
| Client free-chat message → AI agent / conversation turn persistence | The gate is the single choke point deciding whether a client's raw text ever reaches `aiBookingAgent` or gets written to `conversation_turns` |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-27-04 | Spoofing/Tampering | `consent:yes`/`consent:no` callback_query handling | low | accept | A forged/replayed callback can at most set the TAPPING Telegram user's OWN consent flag for the business tied to that bot's already-HMAC-verified webhook — the UPDATE targets exactly `(business.id, senderTelegramId)` derived from authenticated context, never from client-supplied ids; no cross-tenant or cross-client escalation is possible, and re-accepting an already-true flag is a harmless idempotent no-op |
| T-27-05 | Repudiation/Integrity | Race between a concurrent first-contact message and the consent:yes callback | low | mitigate | Verified unchanged in Plan 27-01: `insertClientBusinessRelationship`'s `onConflictDoUpdate` SET clause still excludes `consentGiven`, so a concurrent message-triggered upsert can never silently overwrite an already-true `consentGiven` back to false, nor grant it early (PITFALLS.md Pitfall 3 — confirmed still holds, not re-derived) |
| T-27-06 | Denial of Service (self-inflicted) | Client taps Όχι and is blocked from all bot functionality | low | accept | Fully recoverable by design (D-02): the gate re-appears on the client's very next `/start` or free-chat message since `consentGiven` stays false until accepted — no support intervention needed |
| T-27-07 | Information Disclosure | Consent prompt / decline-ack Greek text content | low | mitigate | Verified the composed templates (`CONSENT_PROMPT_GREEK_TEMPLATE`, `CONSENT_DECLINE_ACK_GREEK`) contain only the business's display name — no internal ids, tokens, or secrets are ever interpolated into client-facing text |
| T-27-08 | Elevation of Privilege | Edge case: a crafted `consent:yes`/`consent:no` callback for a (business, sender) pair that has never actually messaged before | low | accept | Requires already knowing the correct per-bot `webhookId` + HMAC secret (gated far upstream by Step 3 of `handleTelegramWebhookPost`); worst case is a no-op UPDATE affecting zero rows, or `showClientRootMenu` rendering for a sender with no real prior relationship row — no data leak, no mutation of another business's or another client's data |

No new package-manager installs occur in this plan (uses only already-installed project code) — the Package Legitimacy Gate and `T-{phase}-SC` row are not applicable here.
</threat_model>
