<objective>
Repurpose the existing `client_business_relationships.consent_given` column (COMP-02, D-01/D-04) from an implied-consent-by-default flag to an explicit-opt-in-required flag: flip its schema default from `true` to `false`, ship the migration that applies this to the live Neon DB with a defensive backfill for pre-existing rows, and update the query layer so a fresh row genuinely starts unconsented while the existing race-safe atomic upsert (PITFALLS.md Pitfall 3) stays untouched.

Purpose: This is the data-layer foundation Plan 27-02's hard consent gate depends on — without the schema default actually flipping on the live DB, the gate Plan 27-02 wires up would silently never fire (every "first contact" would still read back as already-consented).
Output: Updated `src/database/schema.ts`, new `migrations/0013_client_consent_gate.sql` applied to the live Neon DB, and an updated `src/database/queries.ts` with the new `updateClientConsentGiven` write path.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-27-01 | Tampering | migrations/0013's backfill UPDATE statement | low | mitigate | The backfill uses an explicit `WHERE consent_given IS DISTINCT FROM true` scope (never a blanket UPDATE with no WHERE), so even if re-run or run out of order it can only ever set already-true rows to true — it can never touch a row that has genuinely been set false by the app-layer gate (Plan 27-02) |
| T-27-02 | Repudiation/Integrity | migration idempotency | low | mitigate | `ALTER COLUMN ... DROP DEFAULT` / `SET DEFAULT` are naturally idempotent (safe to re-run); the backfill's narrowing WHERE clause is also safe to re-run — Task 3 can be retried without risk if it fails partway |
| T-27-03 | Tampering (injection) | Task 3's Node.js `pg` Client invocation | low | mitigate | The migration SQL is read verbatim from a static, version-controlled file via `fs.readFileSync` and passed directly to `client.query(sql)` — no string concatenation of untrusted/dynamic input into the SQL text at any point |
| T-27-04 | Information Disclosure | Task 3's console output | medium | mitigate | The action explicitly forbids printing `DATABASE_URL` (or any other secret) to console output; only the read-only verification query's result rows (a boolean-ish column_default value) are logged |

No new package-manager installs occur in this plan (uses only already-installed `pg`/`dotenv`/`drizzle-orm`) — the Package Legitimacy Gate and `T-{phase}-SC` row are not applicable here.
