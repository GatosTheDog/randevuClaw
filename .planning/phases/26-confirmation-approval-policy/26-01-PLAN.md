<objective>
Reverse the Phase 22 auto-confirm decision for session-class reschedules (CONF-02): a client rescheduling a session-based booking must go through the same owner approve/reject cascade already used for brand-new session bookings, and a rejected reschedule must never leave the client with zero active bookings.

Schema note (verified directly, per the planning orchestrator's schema-push check): `src/database/schema.ts:178` already has a `rescheduledFromBookingId` column on the `bookings` table (added in an earlier phase for the non-session reschedule flow). This plan wires that EXISTING column into the session-booking code path — it does not add, alter, or remove any schema field, so **no migration / `drizzle-kit push` task is required**.

Purpose: Closes a real product gap (the folded todo `2026-07-27-require-owner-approval-on-reschedule-not-just-new-bookings.md`) where a client could reschedule a session booking and have it silently auto-confirm, bypassing the owner's say entirely — inconsistent with every other session-booking mutation in the app since Phase 22.

Output: `bookSessionInstance` accepts and persists a booking-to-booking link; `rescheduleSessionTool` defers the old booking's cancellation to owner approval time instead of cancelling it immediately; `sbk:approve` cascade-cancels the superseded booking exactly once, mirroring the existing non-session reschedule cascade already in production.
</objective>

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-26-01 | Tampering | sbk:approve/reject callback_data (bookingId only) | low | accept | callback_data still carries only a bookingId (unchanged by this plan); the existing ownership + cross-tenant guards (T-22-01/T-22-02) and the CAS gate (updateBookingStatusIfPending) are untouched and still run before the new cascade code executes |
| T-26-02 | Tampering / Elevation of Privilege | sbk:approve's new `updateBookingStatus(updated.rescheduledFromBookingId, 'cancelled')` has no explicit businessId WHERE clause | low | accept | Mirrors the existing, already-shipped cascade pattern in the same file's plain approve_/reject_ block, which relies solely on the ambient `withBusinessContext(business.id, ...)` RLS scope wrapping the whole `handleCallbackQuery` call — a foreign-business rescheduledFromBookingId would match 0 rows under RLS, not leak. | T-26-03 | Repudiation (double-tap race) | Two near-simultaneous sbk:approve taps on the same rescheduled booking | low | mitigate | Already covered structurally: updateBookingStatusIfPending's WHERE-guarded CAS means only the first tap's `updated` is non-null; a second tap returns null and exits before ever reaching the new cascade code, so the cascade can execute at most once per booking |

During the pending window the client's membership is debited once for the original booking and again for the new pending booking; on approval only the new booking's debit remains charged.
