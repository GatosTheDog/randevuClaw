<objective>
Establish the single owner-confirmation model for CONF-01: one constants file for button labels (D-07), one module that owns the five confirmation prompts and their execute-on-confirm handlers (D-04, D-05, D-06), and routing through the existing `menu:` callback namespace so no top-level callback prefix or parser change is needed. The admin-menu cancel-class confirmation is converged onto the same contextual-label model so that the free-chat path (plan 26-02) reuses it unchanged.

Purpose: nothing destructive mutates until the owner taps an explicit confirm button, whether the request began in `/menu` or in free chat. This plan delivers everything the tools in plan 26-02 will call.
Output: `src/utils/greek-messages.ts`, `src/telegram/handlers/owner-confirm.ts`, updated `src/telegram/handlers/admin-menu.ts`, and four test files.

Planner decisions recorded here (not in CONTEXT, honoring its Claude's-Discretion list):
- `assign_client_to_session` reads as an add/commit action, not an approval, so it uses the contextual pair Ανάθεση/Άκυρο rather than Έγκριση/Απόρριψη (RESEARCH open question 1 recommended the approve pair; nothing is pending approval here, so the contextual label is clearer).
- D-04 literally says "close_day (update_hours)". Both tools overwrite stored weekly hours, so both are gated under one confirmation class; this is the same list item, not an expansion. Surfaced as an assumption in the return message.
- RESEARCH proposed a `PENDING_CONFIRMATION:` sentinel string plus a prompt instruction. Superseded: the codebase already has the "tool sends its own keyboard and returns an empty string to break the Gemini loop" pattern (create_package, record_payment), which cannot loop and does not depend on model compliance. Plan 26-02 uses it.
- RESEARCH's `menu:confirm_price:<id>:<cents>` shape does not survive the shared `menu:` parser (the parser takes only one trailing numeric segment as `id` and leaves the rest inside `menuAction`). The grammar below is designed around that parser behavior, and the handler reconstructs the raw string before matching.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram callback_query to webhook | callback_data is attacker-influenced text until re-validated; the sender identity is the Telegram-authenticated `from.id` behind the per-bot HMAC secret |
| callback_data to database | numeric ids and values embedded in menu:confirm:* strings reach SQL only after parsing, range validation and a business-scoped re-read |
| Owner chat to client chat | the assign handler sends a Telegram message to an arbitrary client id supplied inside callback_data |
