<objective>
Build the CONF-02 domain core: persist the reschedule link on session bookings, and implement the approve-time cascade that cancels the original booking, settles credit net-zero, releases the original's capacity, and degrades safely when the original is no longer active. Make the two-hour expiry notice reschedule-aware. Everything is exercised against real Postgres.

Purpose: D-02/D-03 require the original booking to be held until the replacement is approved. This plan provides the primitives (no tool, webhook or prompt changes yet; those are plans 26-04 and 26-05).
Output: updated `src/session/manager.ts`, `src/database/queries.ts`, `src/conversation/expiry-poller.ts`, extended fixtures, three integration test files.

Credit design decision (resolves RESEARCH CORRECTION and orchestrator findings 1 and 2):
- Under D-03 as written, a replacement that deducts on insert while the original keeps its credit double-charges on approve and wrongly refuses the last-credit reschedule under enforcement_policy=block.
- Chosen design: the replacement is created with NO deduction (explicit null membership), so reject and expiry need no new code and the existing restore paths find no ledger row. At approve, inside the same transaction, the original's credit is restored first (key `booking:<oldId>:credit`) and the approved replacement is deducted second (key `booking:<newId>:deduction`). Restore-then-deduct means the counter never needs to be negative, so the last-credit case works under every policy.
- Billing parity: when the original had never been charged (unlimited membership, no membership at booking time), the replacement is not charged either. When the original is already inactive, the replacement is charged as a new booking if a finite membership with sessions remaining exists (the original's own cancel path already refunded or forfeited its credit).
- The legacy non-session reschedule cascade (src/webhooks/telegram.ts approve_<id> block) never releases capacity for the old booking and, because it links the ledger at creation, would refund on reject; both are out of scope here and listed as deferred in the return message.
</objective>
