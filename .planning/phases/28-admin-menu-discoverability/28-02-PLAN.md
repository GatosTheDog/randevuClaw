Wire the escalation "reply" button (ADMIN-01) into a real message relay: staging the pending reply when the owner taps the button (D-01/D-02), consuming it on the owner's next free-text message to forward that text to the escalating client (D-05: text only, no media), and clearing it on navigation (D-03). Per D-13, no Phase 26 Ναι/Όχι confirmation pattern is added here — the relay send and its confirmation message are non-destructive/reversible and fall outside Phase 26's CONF-01 scope.

Purpose: Closes the gap where tapping "reply" today (Phase 20) only prompts the owner and stops — the owner's actual reply text currently has no code path to the client at all.
Output: A new pending-reply state module (mirroring the proven pendingServicePriceChanges pattern) and the telegram.ts wiring that makes the full escalation-reply loop actually deliver messages.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Escalation reply prompt → owner's next free-text message | The relay intercept trusts that the NEXT message from a given ownerTelegramId (after that owner's own escl:reply tap) is the reply text — no additional re-confirmation step distinguishes "this is definitely the reply" from "this is an unrelated message the owner happened to send next" |
| Pending-reply Map → per-owner isolation | pendingReplies is keyed by ownerTelegramId; consumePendingReply(senderTelegramId) can only ever read/consume the entry keyed to the CALLING owner's own authenticated Telegram id |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-28-04 | Tampering | `escl:reply` callback → `stagePendingReply` | low | accept | Reached only through the pre-existing owner-only guard in `handleCallbackQuery`'s `escalationAction` branch (`business.ownerTelegramId !== senderTelegramId` check) — unchanged from the existing pattern, this plan adds no new guard surface here |
| T-28-05 | Spoofing / Information Disclosure | Cross-owner pending-reply Map key collision | medium | mitigate | `pendingReplies` is keyed by `ownerTelegramId` (never a shared/global key) — one owner's staged `clientTelegramId` is structurally unreachable from another owner's `consumePendingReply(senderTelegramId)` call, since the Map lookup uses the calling owner's own authenticated id |
| T-28-06 | Repudiation / Reliability | In-memory Map state lost on process restart | low | accept | D-02 explicitly accepts this: no persistence, no schema change; the owner's only recourse is to re-tap the reply button — a UX hiccup, not a data-integrity or security issue, and is documented in pending-reply.ts's header comment |
| T-28-07 | Tampering (message content) | Relayed message text is the owner's own free-text input, unvalidated/unsanitized before forwarding | low | accept | `messageText` originates from the owner's own authenticated Telegram client (not from any external or client-supplied source) — the only realistic failure mode is the owner accidentally sending the wrong text to the wrong escalation, a user-error risk, not a code-level tampering vector |
| T-28-08 | Denial of Service (unbounded growth) | `pendingReplies` Map entries accumulating across many escalations | low | accept | Each entry auto-expires after a 10-minute `.unref()`'d timeout, and `stagePendingReply` overwrites (never duplicates) any existing entry for the same `ownerTelegramId` — Map size is bounded by the number of DISTINCT owners with an active pending reply, not by total escalation volume |

No new package-manager installs occur in this plan (uses only already-installed project code) — the Package Legitimacy Gate and `T-28-SC` row are not applicable here.
</threat_model>
