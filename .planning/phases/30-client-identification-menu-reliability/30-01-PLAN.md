<objective>
Convert the 4 raw-Telegram-ID-requiring owner tools in `src/onboarding/ai-owner-agent.ts` — `view_client_membership`, `assign_client_to_session`, `send_renewal_reminder`, `list_slotless_requests` — to accept a client name instead, with text-based disambiguation when a name matches 2+ clients and a generic reply when it matches none (UX-03, D-01 through D-05).

Purpose: Owners currently must copy a raw Telegram numeric ID out of another message to use these 4 tools. That's the exact friction UX-03 exists to remove — the owner should be able to just type the client's name, the same way they already do for service/package names elsewhere in this file.

Output: All 4 tools accept `client_name`; one shared name-resolution helper handles matching/disambiguation/RLS-scoping for all of them; `tests/ai-owner-name-matching.test.ts` proves single-match, zero-match, ambiguous-match, case-insensitivity, and cross-business isolation.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Owner (Telegram, HMAC-verified webhook) → Gemini tool call → `getAllClientsForBusiness` | Owner-supplied free text is parsed by Gemini into a `client_name` string, which becomes a DB filter predicate scoped by `business.id`. |
| Gemini tool-result text → owner's Telegram client | The disambiguation list and error strings returned by the tool are narrated back to the owner by Gemini — must never leak internal identifiers. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|--------------|------------------|
| T-30-01 | Elevation of Privilege / Information Disclosure | `resolveClientByName` → `getAllClientsForBusiness` | high | mitigate | `resolveClientByName` always invokes `getAllClientsForBusiness` with the caller's own `business.id`, wrapped in `withBusinessContext(business.id, ...)` for RLS enforcement — never with an owner-supplied ID. `getAllClientsForBusiness` itself also has an explicit `WHERE businessId = ...` clause (defense in depth, two independent layers). Verified by Task 1's cross-business isolation test: a same-named client fixture under a different mocked businessId never resolves under `MOCK_BUSINESS.id`. |
| T-30-02 | Denial of Service | `resolveClientByName` (Zod input validation) | medium | mitigate | `ClientNameInputSchema` (`z.string().trim().min(1).max(100)`) rejects empty or oversized Gemini-parsed name strings before any DB query — an unbounded string can never reach `getAllClientsForBusiness`'s filter. |
| T-30-03 | Information Disclosure | `formatClientDisambiguation` | low | mitigate | The disambiguation string is built strictly from `matches.map(m => m.clientName)` (D-05) — `senderPhone` (the internal Telegram ID) is never interpolated. Covered by an explicit assertion in the new test that the returned text never contains the fixture's mocked `senderPhone` value. |
</threat_model>
