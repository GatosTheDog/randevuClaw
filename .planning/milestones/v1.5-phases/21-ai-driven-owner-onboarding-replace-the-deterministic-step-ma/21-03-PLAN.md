<objective>
Delete the now-fully-replaced deterministic onboarding step machine (`src/onboarding/steps.ts`,
`src/onboarding/router.ts`) and the session-lifecycle functions in `src/onboarding/queries.ts`
that only existed to serve it, now that Plans 21-01/21-02 have built and wired

nothing references the deleted modules, and remove one pre-existing broken test file that
predates this phase but is directly entangled with the modules being deleted.

## Resolved scope decisions (21-CONTEXT.md open questions)

1. **`src/onboarding/edit-router.ts` — OUT of scope for this phase.** Verified during
   planning: `routeOwnerEdit`/`hasPendingEditState`/`isOwnerEditCommand` are never called
   from `src/webhooks/telegram.ts` or anywhere else in `src/` (grep confirms zero call
   sites outside the file itself and its direct unit test) — this module is already dead
   code, not a live parallel path to `aiOwnerAgent`. Its stated purpose (post-onboarding
   hours/service editing via chat) is already fully covered by `aiOwnerAgent`'s existing
   `update_hours`/`add_service`/`update_service_price`/`delete_service` tools. Because it is
   unreachable, it carries zero regression risk either way; this plan leaves the file as-is
   (no deletion, no AI rewrite) and only relocates its still-valid unit test coverage
   (isOwnerEditCommand, ONB-03) out of the onboarding-flow.test.ts file being deleted, so
   that coverage is not lost. Rewiring or removing edit-router.ts entirely is left as a
   separate follow-up if ever needed — not required by this phase's goal.
2. **`onboarding_sessions.currentStep`/`collectedData` columns (and the table as a whole)
   — left INERT, no migration this phase.** Once `updateOnboardingStep` /
   `createOrResetOnboardingSession` / `findActiveSessionByOwnerTelegramId` are removed in
   this plan (Task 1), nothing in the codebase reads or writes `onboarding_sessions` at all
   — the table becomes fully unused, not just those two columns. A `schema.ts` migration to
   drop it would require a `drizzle-kit push` against the live Neon DB for a
   zero-functional-benefit cleanup; the risk/reward does not justify it in this phase. The
   table is left in place, unused, for a future housekeeping pass.
</objective>
