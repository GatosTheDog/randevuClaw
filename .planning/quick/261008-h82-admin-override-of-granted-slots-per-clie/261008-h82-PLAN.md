<objective>
Let the business owner choose how many classes (slots) a specific client has, independent of the package the client paid for. Real-world cases: the client paid for an 8-class package but the owner agreed in person to give 12 for the same price (discount); or the client paid for 8 but the owner, for some reason, will only give 6.

Purpose: today the only way a membership's class count is set is `createMembership` copying `billing_packages.session_count`; there is no owner path to deviate from it. This adds one owner-facing Greek chat tool that adjusts the client's active membership balance safely.

Output: one DB query (`adjustMembershipSessions`), one handler + zod schema (`handleSetClientSlots`), one owner AI tool (`set_client_slots`) wired through the existing name-based client resolution, and three test files.

Design decisions made by the planner (no CONTEXT.md exists for this quick task, so nothing here overrides a locked user decision):
- Surface: the owner's free-text Gemini agent (`aiOwnerAgent`), the same surface as `view_client_membership`, `record_payment`, `set_enforcement_policy`. No new inline-keyboard or text-input state machine.
- Semantics: the override changes the membership's remaining-balance counter (`memberships.sessions_remaining`), because that is the single number every booking, cancel, display and nudge path already reads. There is no "granted total" column and the ledger cannot reconstruct one (renewals reuse the same membership row, so ledger sums span renewals); hence two modes instead of a "total" mode: `set` (balance becomes exactly N) and `add` (signed difference). "Paid 8, give 12" = add +4, which is correct whether or not the client already used classes.
- The override applies to the CURRENT membership period. `createMembership` (renewal) still resets the counter from the package, exactly as before; the success reply tells the owner this. The owner re-applies the override after a renewal. (Whether a standing per-client override that survives renewals is wanted is an open product question, not specified in the request; it would need a schema change and is intentionally not built here.)
- No confirmation keyboard: Phase 26 locked the confirmation policy scope to exactly five named actions and said not to widen it without re-discussion. The reply instead echoes the exact before and after numbers, the change is reversible by repeating the command, and the ledger records it.
- The client is not messaged about the change (the agreement happens in person; an unrequested outbound message would also go to a client who may not expect it).
- Allowed targets: a client with an active, non-expired membership only (same predicate as booking deduction). Otherwise the owner is told to record a payment first.
</objective>
