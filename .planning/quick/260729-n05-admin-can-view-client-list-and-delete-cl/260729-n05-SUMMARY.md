# Quick Task 260729-n05: Admin client deletion + settings label fixes Summary

**GDPR-style client full-erase (8-table cascade) + unlink-only action wired into the admin Telegram menu, plus 4 corrected Greek toggle-button labels in Ρυθμίσεις**

## Performance

- **Duration:** ~35 min
- **Completed:** 2026-07-29
- **Tasks:** 3/3
- **Files modified:** 4 (2 new + 2 modified test files, 3 source files modified)

## Accomplishments

- Business owner can now tap "Πλήρης διαγραφή" from a client's balance screen to permanently delete every DB row tied to that client for this business (memberships, ledger, notifications, bookings, slotless requests, conversation history, and the relationship row itself) — an 8-table FK-safe cascade, with no message sent to the client's own chat.
- Business owner can tap "Αφαίρεση από λίστα" to unlink a client (delete only the `clientBusinessRelationships` row) while preserving all booking/membership history.
- Both destructive actions are gated behind a Ναι/Όχι confirmation naming the client, and both re-verify `rel.businessId === business.id` at both the handler layer and the query layer before any mutation (defense-in-depth, per the threat model's T-quick-01/T-quick-02).
- Fixed 4 nonsensical/incomplete Greek toggle-button labels in the settings sub-menu (missing "χωρίς", raw English "cutoff", the wrong word "Επιτροπή" [committee], and a vague objectless "ειδοποίηση").

## Files Created/Modified

- `src/billing/queries.ts` - Added `deleteClientBillingData(businessId, clientPhone)`: deletes membershipLedger, membershipExpiryNotifications, renewalNudgeNotifications (scoped to the client's membership id(s)), then the memberships row(s).
- `src/database/queries.ts` - Added `deleteClientBookingData(businessId, clientPhone)` (deletes slotlessRequests, then bookings, then conversationTurns, in FK-safe order) and `deleteClientBusinessRelationship(relId, businessId)` (ownership-guarded DELETE returning a boolean).
- `src/telegram/handlers/admin-menu.ts` - `showClientBalance` now always renders both new buttons; 4 new handlers (`showDeleteFullConfirm`, `handleDeleteFullExecute`, `showUnlinkConfirm`, `handleUnlinkExecute`); 6 new `handleMenuCallback` switch cases; 4 `showSettingsMenu` toggle-button label strings corrected.
- `tests/client-delete-queries.test.ts` - New real-DB integration test file: full-erase cascade (all 8 tables empty afterward), unlink-only preserves membership/booking history, cross-tenant `deleteClientBusinessRelationship` call rejected.
- `tests/admin-menu.test.ts` - 3 new describe blocks (button rendering in both membership states, full-erase ownership guard + happy path, unlink ownership guard + happy path) plus 2 new assertions on the corrected settings labels (both toggle directions of the multi-booking toggle).

## Decisions Made

- `deleteClientBillingData`/`deleteClientBookingData` use `getConn()` (not `db.transaction()`) — atomicity for the multi-table full-erase comes from the outer `withBusinessContext` transaction already open in `handleCallbackQuery` (telegram.ts), matching the established `restoreCredit`/`deductSession` pattern.
- `deleteClientBusinessRelationship`'s DELETE WHERE clause includes `businessId` as an independent, defense-in-depth ownership check — a forged `relId` for another business matches zero rows at the query layer even if the handler-layer check were somehow bypassed.
- `handleSettingsToggle`'s 8 confirmation-message strings were checked against the same "complete, grammatically correct Greek" standard used for the button labels and found already correct — left untouched per the plan's explicit instruction.
