<objective>
Add two independent layers of Neon free-tier cold-start resilience to the database layer, based on today's live production incident (recurring "Connection terminated due to connection timeout: Connection terminated unexpectedly" errors hitting `findBusinessByWebhookId`, `listAllBusinessIds` from 4 pollers, and `runInTransaction`'s initial `pool.connect()` inside `withBusinessContext`):

1. A lightweight keep-alive poller that pings both `pool` and `appPool` with `SELECT 1` every ~90 seconds, reducing how often Neon's compute has actually gone fully idle/suspended by the time a real request arrives.
2. A narrowly-scoped retry-with-backoff helper for the specific "Connection terminated" transient error class, applied ONLY at safe boundaries: `runInTransaction`'s bare connection-acquisition step (before the transaction callback runs, so a retry can never re-execute a callback with side effects like Telegram sends) and the two pure-read query functions that failed in production today.

Purpose: Reduce the frequency and blast radius of Neon compute-suspend/cold-start connection failures without reintroducing either of the two previously-fixed connection-lifecycle bugs in this exact area (the checked-out-client leak from query-read-timeout-storm, and the missing-error-listener crash from db-idle-transaction-crash).

Cross-reference that the retry helper below intentionally never wraps a transaction callback, to avoid reintroducing the query-read-timeout-storm leak class.

Export `function isTransientConnectionError(err: unknown): boolean`. Walk the error and its `cause` chain (bounded by a `Set` of already-visited objects to prevent an infinite loop on a circular `cause`): starting from `err`, while the current value is a non-null object not already visited, check whether its `message` property is a string containing the substring `'Connection terminated'` — if so return `true`; otherwise move to its `.cause` property (may be `undefined`, ending the walk) and continue. Return `false` if the walk ends with no match. This matches all observed production variants (e.g. a message containing exactly `'Connection terminated due to connection timeout: Connection terminated unexpectedly'`) since they all contain the substring, and also covers a wrapped/nested error surfaced via `Error.cause`.

Export `async function withConnectionRetry<T>(fn: () => Promise<T>, maxRetries = 2, retryDelaysMs: number[] = [300, 800]): Promise<T>`. Loop `attempt` from `0` to `maxRetries` inclusive: call `await fn()` inside a try/catch; on success return the result immediately. On failure: if `isTransientConnectionError(err)` is `false`, OR `attempt === maxRetries` (no attempts remain), rethrow `err` immediately unchanged — never swallow or wrap it. Otherwise (transient error with attempts remaining), log via `logger.warn({ err, attempt: attempt + 1, maxRetries }, 'Transient DB connection error, retrying')`, wait `retryDelaysMs[attempt] ?? retryDelaysMs[retryDelaysMs.length - 1] ?? 0` milliseconds via a `setTimeout`-wrapped `Promise`, then continue the loop for the next attempt. The `retryDelaysMs` parameter defaults to `[300, 800]` per this task's spec but is overridable so tests can use near-zero delays without changing production behavior — this is a superset of the required 2-argument call shape (`withConnectionRetry(() => pool.connect())` and `withConnectionRetry(() => db.select(...))` both still work unchanged with the default).

Change `runInTransaction`'s very first statement from `const client = await pool.connect();` to `const client = await withConnectionRetry(() => pool.connect());`. Do not change anything else in `runInTransaction` — the `try { return (await clientDb.transaction(callback as never)) as T; } catch (err) { ... } finally { client.release(...) }` block that follows is untouched, and only ever runs after a client has already been successfully obtained (whether on the first attempt or a retried one). Because a failed `pool.connect()` attempt never returns a client, there is nothing to leak or release on a failed retry attempt — the existing leak-prevention guarantee from query-read-timeout-storm (client.release() in the try/finally around `clientDb.transaction`) is completely unaffected, since that guarantee only ever applied to code that runs strictly after this line.

In `src/database/queries.ts`, update the import on line 3 from `import { db, appPool, runInTransaction } from './db';` to also include `withConnectionRetry`. In `findBusinessByWebhookId` (lines 101-108), wrap the existing `db.select().from(businesses).where(eq(businesses.webhookId, webhookId)).limit(1)` expression in `withConnectionRetry(() => ...)`, keeping the rest of the function (the `rows[0] ?? null` return) unchanged. In `listAllBusinessIds` (lines 530-533), wrap the existing `db.select({ id: businesses.id }).from(businesses)` expression in `withConnectionRetry(() => ...)`, keeping the `.map((row) => row.id)` line unchanged. Do not add retry to any other query function, and do not wrap `runInTransaction`'s transaction callback, `withBusinessContext`'s callback, or any function in `src/session/manager.ts` — those are explicitly out of scope.
